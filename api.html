API Reference#

Base URL#

The server listens on http://<host>:<port>.

POST /generate#

Generate speech from text (and optional audio) and return a WAV response.

Parameters (multipart form)#

  • text (string, required): Input prompt.

  • audio (file, optional): Input audio for STS-capable models. The Rust runtime accepts request bodies up to 100 MiB.

  • streaming (bool, optional, default true): - true streams WAV chunks as they are produced. - false returns a single WAV file after completion.

Response#

  • Streaming mode: audio/wav with chunked transfer. With the Rust runtime, a request that fails after streaming has started (an error, the timeout, or its engine stopping) aborts the connection instead of ending the body cleanly, so truncated audio is never reported as complete.

  • Non-streaming mode: audio/wav file download.

Examples#

curl -X POST "http://localhost:8000/generate" \
  -F "text=Hello world" \
  -F "streaming=true" \
  -o output.wav

curl -X POST "http://localhost:8000/generate" \
  -F "text=Hello world" \
  -F "audio=@input.wav" \
  -F "streaming=true" \
  -o output.wav

GET /health#

Health check endpoint.

Response#

JSON payload:

{"status": "healthy"}

With the Rust runtime, once an engine has stopped (e.g. after a CUDA error) the endpoint returns 503 with {"status": "unhealthy", "failed_engines": [<rank>, ...]} until the server is restarted; requests are routed to the remaining engines, or get 503 when none is left.

Python API#

Package overview#

vox_serve

VoxServe: A serving system for Speech Language Models.

Key modules#

vox-serve: one command for the Rust and the Python serving runtime.

--runtime auto (the default) serves with the Rust runtime (the vox_serve._rt extension) and falls back to the Python runtime (vox_serve.launch) when the Rust one cannot serve the command line: the extension was not built (its build is optional at install time) or does not load, it was built against another FlashInfer version, or an argument exists only in the Python runtime. Without the extension, arguments only the Rust runtime has are ignored with a warning. --runtime rust and --runtime python pick one runtime without fallback. Errors after start-up never switch runtimes.

Common structure of a graph program: the static buffers and captured stages of one model.

A program owns the model weights and every persistent device buffer (KV cache, per-slot sampling state), declares the input/output arena fields and captures one CUDA graph per stage and shape bucket. The Rust runtime only ever sees the exported arenas, graph handles and meta.

Conventions shared by every LM program (and relied on by the Rust runtime):

  • rows: one row per token position processed this step. tok[r] holds the token ids (all codebooks) of row r unless fb[r] != 0, in which case the ids are read on device from last_tok[row_slot[r]] (the request’s previously sampled token), so the CPU never has to wait for the previous step’s output before launching the next one.

  • requests: N per-request entries per graph. last_row[i] selects the row whose hidden state feeds the LM head for request i. Inactive / padding entries have active[i] = 0 and use the dummy slot max_slots.

  • KV page 0 is a scratch page reserved for padding rows; the runtime never hands it to a request.

  • out_kind[i]: what request i’s sampled row is (TOKEN_AUDIO / TOKEN_STOP / TOKEN_OTHER), computed in the graph by token_kind. The Rust runtime reads it and never interprets token ids itself; its only per-model code builds prompts (rust/src/models).
