Development#

Local setup#

pip install -e .

This also builds the Rust runtime (the vox_serve._rt extension) when a Rust toolchain and the CUDA compiler are available (Installing the Rust runtime); otherwise it is skipped and vox-serve runs the Python runtime. Python changes take effect immediately. After changing anything under rust/, run pip install -e . again; VOX_CUDA_ARCHS=90 (one GPU architecture) makes that build faster.

Run the server#

vox-serve --model <model-name> --port 8000                    # Rust runtime (Python if unavailable)
vox-serve --runtime python --model <model-name> --port 8000   # Python runtime

Repository layout#

  • vox_serve/model/<name>/: the models, one program each, used by both runtimes (Adding a Model).

  • vox_serve/rt/: what the programs share (base program, graph capture, sampling kernels, prompts).

  • vox_serve/fusion/: fused kernels behind the --fuse-* flags.

  • vox_serve/launch.py, vox_serve/scheduler/, vox_serve/worker/: the Python runtime.

  • vox_serve/cli.py: the vox-serve command, which picks the runtime.

  • rust/: the Rust runtime (crate vox-rt): src/server.rs (HTTP), src/scheduler.rs and src/deadline.rs (policies), src/v2.rs (asynchronous lanes and SM partitions), src/engine.rs (graph launches), src/flashinfer.rs + csrc/fi_plan.cu (attention planning), csrc/sampling.cu (sampling kernels, also used by the Python runtime), src/models/ (prompt builders), third_party/flashinfer (vendored FlashInfer headers).

Checks#

Python, with the ruff version CI uses (pinned in the lint dependency group of pyproject.toml):

pip install --group lint        # or: uv pip install --group lint
ruff check .
ruff format .                   # not enforced by CI yet; format the files you change

Rust (formatting settings in rust/rustfmt.toml):

cd rust
cargo fmt
cargo clippy --release --all-targets -- -D warnings
cargo test --release

The Rust unit tests cover what runs without a GPU: scheduling-policy math, text normalization of the prompt builders and the feature-pool allocator. Building the crate compiles CUDA sources, so nvcc is needed even for these checks.

Tests#

python -m pytest tests

The tests run on CPU, without a GPU or model weights:

  • test_schedulers.py runs the Python runtime’s schedulers (base, online, offline; with and without --async-scheduling) against FakeWorker (tests/scheduler_sim.py), a stand-in for ProgramWorker with its slot and completion rules, over real ZMQ sockets. Each workload (streaming and non-streaming requests, more requests than slots, stateful codecs, overlapping chunks, failed prompts) must complete every request with all its audio, in order, and free every slot.

  • test_program_worker.py checks how ProgramWorker batches codec chunks (never two chunks of one request in a batch for stateful codecs).

  • test_prompt_parity.py checks that each model’s Rust prompt builder produces exactly the rows of its program’s preprocess, from the meta recorded in tests/prompt_meta (record.py there re-records it on a GPU) and a small tokenizer generated by the test. It needs the Rust extension and is skipped without it.

The Rust scheduling decisions (online pressing, chunk selection, the offline gate, admission) are unit tests in rust/src/scheduler.rs, next to those of deadline.rs and v2.rs.

Continuous integration#

CI runs on CPU-only GitHub runners, for pull requests (including those from forks; GitHub asks a maintainer to approve runs for first-time contributors) and pushes to main. Pushing again to a pull request cancels its previous run.

  • .github/workflows/ci.yml: ruff check, and pytest tests with CPU-only PyTorch (the prompt parity test is skipped there).

  • .github/workflows/rust.yml, with the Rust version pinned in RUST_TOOLCHAIN (bump it together with the fixes new clippy lints ask for):

    • cargo fmt --check, cargo clippy -D warnings and cargo test, after installing the CUDA compiler and runtime libraries (.github/scripts/install-cuda-toolkit.sh; no GPU or driver needed);

    • the release distributions (dists.yml, below), whose wheel is installed in a clean environment with the CUDA runtime library from nvidia-cuda-runtime-cu12; its vox_serve._rt must load and parse a command line;

    • the prompt parity test against that wheel, with CPU-only PyTorch;

    • a wheel built without CUDA, which must not contain the extension and must fall back to the Python runtime.

  • .github/workflows/dists.yml: the release distributions, built by .github/scripts/build-dists.sh in a manylinux_2_28 container: the sdist, and from it the wheel with the extension, repaired by auditwheel (--exclude libcudart.so.12: a wheel must never bundle the CUDA runtime, the extension shares the one PyTorch loads). The wheel is cp312-abi3, one wheel for every Python version from 3.12. Run it locally (Docker or Podman) with docker run --rm -v "$PWD:/io" -w /io -e RUST_TOOLCHAIN=1.90.0 quay.io/pypa/manylinux_2_28_x86_64 .github/scripts/build-dists.sh dist.

  • .github/workflows/publish.yml: on a published GitHub release, builds the distributions with dists.yml and uploads them to PyPI (trusted publishing).

  • .github/workflows/docs.yml: builds this documentation for pull requests, and builds and publishes it for pushes to main.

There is no GPU test suite. Validate changes that touch the GPU path by serving with both runtimes:

curl -X POST localhost:8000/generate -F "text=Hello world" -F "streaming=true" -o out.wav
vox-serve --runtime rust --model <model-name> --bench-requests 4 --bench-out /tmp/out --greedy
python rust/scripts/asr_check.py /tmp/out/bench_*.wav    # Whisper transcripts
bash rust/scripts/smoke_model.sh <model-name>            # the two steps above

Load benchmarks against a running server are in benchmark/, sample clients in examples/.

Build documentation#

pip install -r docs/requirements.txt
make -C docs html
